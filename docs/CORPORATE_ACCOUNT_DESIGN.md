# 法人アカウント設計（B2B社用車管理）

**状態**: 提案・**未合意**。実装前にオーナー確認が必要（CLAUDE.md の Agree レベル）
**作成**: 2026-08-05

---

## 1. なぜ設計から始めるか

「法人担当者が法人用アカウントで入ると、会社で管理しているクルマの一覧がずらっと見えて、
点検・車検を網羅的に確認できる」——これが求められている姿です。

**現状のアーキテクチャではこれが成立しません。** データ構造を間違えると既存車両データの
移行が必要になり、後戻りが高くつくため、実装前に合意を取ります。

---

## 2. 現状の実測

### あるもの

`FleetDashboardScreen` は実装済みで、中身も揃っています。

| 機能 | 状態 |
|------|------|
| 車両一覧・統計ヘッダー | ✅ |
| 車検一括問い合わせ（60日以内を抽出して工場へ） | ✅ |
| CSV出力 | ✅ |
| 保険概要タイル | ✅ |
| 緊急度フィルタ（`FleetFilter`） | ✅ |

### ないもの

**法人アカウントという概念そのもの。**

```dart
// lib/models/user.dart
final UserPlanType planType;   // free / premium の2値のみ
```

個人か法人かを区別する仕組みがありません。さらに:

```dart
FleetDashboardScreen(companyId: uid)   // ログインユーザーのuidを会社IDに代用
```

**会社という実体が無いため、自分のuidを会社IDとして渡しています。** この構造では

- 同じ会社の複数の担当者が同じ車両一覧を見る
- 担当者の異動・退職時に引き継ぐ
- 部署・拠点ごとに車両を分ける

のいずれもできません。

### 導線

ホームのタブは `マイカー / マーケット / みんなの投稿 / 通知 / プロフィール` で、
**完全にB2C個人向け**です。フリート管理はタブになく、

```dart
/// SMB fleet upsell: shown from the 5th vehicle.
```

**個人ユーザーが5台目を登録して初めて出るアップセルバナー**からしか辿り着けません。
「B2Cアプリに、たくさん車を持っている人向けのオマケがぶら下がっている」構造です。

## 3. 設計方針

### 3.1 データ構造

新設するコレクションは2つです。

#### `companies`

| フィールド | 型 | 説明 |
|-----------|----|----|
| `id` | String | 会社ID（ドキュメントID） |
| `name` | String | 会社名 |
| `inviteCode` | String | 担当者招待用コード（既存の `_FleetCodeTile` を流用） |
| `createdBy` | String | 作成した担当者のuid |
| `createdAt` | Timestamp | |
| `plan` | String | 契約プラン（既存 `fleet_plan.dart` と接続） |

#### `company_members`

会社と担当者の多対多を表します。ユーザーが複数の会社に属する可能性を最初から許容します
（例: グループ会社の兼任、代理店が複数顧客を見る）。

| フィールド | 型 | 説明 |
|-----------|----|----|
| `companyId` | String | |
| `userId` | String | |
| `role` | String | `owner` / `manager` / `viewer` |
| `invitedBy` | String | |
| `joinedAt` | Timestamp | |

**権限の考え方**

| ロール | 車両の閲覧 | 車両の追加・編集 | 担当者の招待・削除 | 契約変更 |
|--------|-----------|----------------|------------------|---------|
| `owner` | ✅ | ✅ | ✅ | ✅ |
| `manager` | ✅ | ✅ | ✅ | ❌ |
| `viewer` | ✅ | ❌ | ❌ | ❌ |

> `viewer` は「現場の運転者に車検期限だけ見せたい」という用途を想定。B2Bでは
> 全員に編集権を渡さない要求が必ず出ます。

#### 既存 `vehicles` への追加

`companyId`（既存）を**正式に使います**。現在は uid が入っている想定なので、移行が必要です（§5）。

`assigneeId` / `assigneeName` は既に存在するので、そのまま「利用者」として使います。

### 3.2 アカウント種別

`User` に追加します。

```dart
enum AccountType { individual, corporate }
final AccountType accountType;   // 既定 individual（既存ユーザーは全員こちら）
```

**既定を `individual` にすることで、既存ユーザーの挙動は一切変わりません。**

### 3.3 ログイン後の分岐

```
ログイン
  ├─ accountType == corporate かつ 所属会社あり
  │     → 会社の車両一覧をトップに表示（FleetDashboard を昇格）
  │        タブ: 車両 / 期限 / 担当者 / 通知 / 設定
  │
  ├─ accountType == corporate だが所属会社なし
  │     → 会社を作る or 招待コードで参加する画面
  │
  └─ accountType == individual
        → 現行のまま（マイカー / マーケット / みんなの投稿 / 通知 / プロフィール）
```

複数会社に所属する場合は、AppBar に会社切替を置きます。

### 3.4 トップ画面の情報設計

**最初に見せるのは「対応が要る車両」です。台数ではありません。**

```
┌─────────────────────────────────┐
│ ○○株式会社            [会社切替] │
├─────────────────────────────────┤
│  3      1       2      18       │  ← タップで絞り込み（実装済み）
│ 期限切  30日内  90日内  正常      │
├─────────────────────────────────┤
│ ⚠ 品川 300 あ 12-34             │
│   トヨタ プリウス / 営業部 田中    │
│   車検 2026-08-20（あと15日）     │
│   [工場に依頼]                   │
├─────────────────────────────────┤
│ ⚠ 品川 500 か 34-56  ...        │
└─────────────────────────────────┘
```

原則:

1. **期限が近い順に並べる。** 台数や登録順ではない
2. **1行で判断に必要な情報を出す** — ナンバー / 車種 / 利用者 / 期限までの日数
3. **その場で次の行動に移れる** — 「工場に依頼」までを一覧から

> 既存の `FleetDashboardScreen` はこの要件をほぼ満たしています。**作り直しではなく昇格**です。

## 4. セキュリティルール

`firestore.rules` に以下が必要です。**新規コレクション追加時はルールを同時に定義する**という
CLAUDE.md の方針に従います。

- `companies`: メンバーのみ読取。`owner` のみ更新
- `company_members`: 同じ会社のメンバーのみ読取。`owner`/`manager` のみ書込
- `vehicles`: 既存の個人所有判定に加え、`companyId` が一致し当該会社のメンバーであれば読取可。
  書込は `owner`/`manager` のみ

> **既存の `vehicle_sharing_permissions`（PR #76 でマージ済み）がこの権限判定の土台**です。
> 今日 #76 をマージ対象に選んだのはこのためです。

必要な複合インデックス:

| コレクション | フィールド |
|-------------|-----------|
| `vehicles` | `companyId` ASC, `inspectionExpiryDate` ASC |
| `company_members` | `userId` ASC, `joinedAt` DESC |
| `company_members` | `companyId` ASC, `role` ASC |

## 5. 移行

**既存データを壊さないことが最優先です。**

1. `AccountType` の既定を `individual` にする。既存ユーザーは何も変わらない
2. `companies` / `company_members` を新設（既存データへの影響なし）
3. 法人アカウントを新規に作る導線だけ先に用意する
4. **既存の「5台以上の個人ユーザー」を法人へ移す導線は、本人の明示的な操作でのみ実行**する。
   自動移行はしない
5. `FleetDashboardScreen(companyId: uid)` の uid 代用は、法人アカウントが実体を持つまで
   そのまま残す。両方が並存できる形にする

> 自動移行を避けるのは、今日の #106 クローズのような「機械的な一括判断で外す」失敗を
> 繰り返さないためです。データの移行は取り返しがつきません。

## 6. シナリオ完走テスト

本設計とあわせて導入します。**判定基準は「表示されるか」ではなく「次に進めるか」です。**

今日見つかった不具合13件のうち、少なくとも7件はこの形式なら初日に検出できました。

```
S1: 法人担当者が車検切れ間近の社用車を工場に依頼する
    ログイン → 車両一覧 → 「期限切れ」タップ → 対象車両 → 工場を探す → 依頼送信
    ※ どこか1ステップでも進めなければ失敗

S2: 担当者を招待して viewer 権限で共有する
    設定 → 担当者 → 招待コード発行 → 別ユーザーが参加 → 車両一覧が見える
    → 編集操作が拒否される

S3: カタログに無い車を登録する
    車両追加 → メーカー「BMW」→ 一覧に無い → 手入力 → 車種手入力 → 登録完了
    ※ 本日修正済み。回帰防止として固定化する

S4: 無料ユーザーがPDF出力を試みてプレミアムに登録する
    PDFボタン → 制限ダイアログ → 登録導線 → 購入完了 → PDF出力成功
    ※ 本日まで profile_screen 側が行き止まりだった

S5: 整備記録を追加して一覧に反映される
    記録追加 → 保存 → タイムラインに出る
    ※ 読み込み失敗時に「記録がありません」と出さないことも検証する
```

## 7. 未決定事項（オーナー判断が必要）

| # | 論点 | 選択肢 |
|---|------|--------|
| 1 | 法人アカウントの作り方 | 自己申告で作成 / 審査を挟む |
| 2 | 課金単位 | 会社単位（台数課金） / 担当者単位 |
| 3 | 個人ユーザーとの関係 | B2Cを維持し併存 / B2Cを段階的に縮小 |
| 4 | `viewer` ロールの要否 | 初期から用意 / owner・manager のみで開始 |
| 5 | 複数会社所属 | 初期から許容 / 1ユーザー1会社に限定して簡素化 |
| 6 | B2B向け利用規約 | 現行の消費者向け規約では、法人契約の責任制限・SLA・データ帰属が不足 |

**特に2と3は事業判断**で、技術的にはどちらでも組めます。ここが決まらないと課金まわりの
実装に入れません。
