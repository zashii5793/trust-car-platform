4コンセプトとの整合性

企画のコンセプトは 「クルマをもっと安全に、楽しく、個性的に。」、 設計思想は 「主役は常にユーザー。AIは判断しない。理由を添えて選択肢を整理するだけ」。 これがコードでどこまで守られているかを照合した。

4-1. 3つの価値軸との対応

価値軸企画上の約束実装判定
安全見落とさない安心。車検／保険の期限、整備記録、OCR期限アラート（3段階の色分け）、走行距離ベースの整備推奨、車検証OCR、貨物車の車検周期を登録時から反映、安全情報ティップス整合 最も厚く実装されている軸
楽しくクルマのある生活の喜び。ドライブログ、SNS、愛車タイムライン3つとも実装済み。加えて「この1年のふりかえり」で溜めた記録を体験として返す整合
個性的に自分だけの一台への誇り。AIパーツ提案、BtoBマーケット、カスタム履歴パーツ提案・マーケット・アクセサリーのシェアは実装済み。ただし提案の「理由の構造」が企画と違う（下記4-3）部分整合

4-2. 設計思想が守られている点

原則コード上の裏付け
AIは提案する、決めないホーム画面のAI提案は理由全文を出す詳細シートを持ち、断定表現を避ける。AI出力には AiDisclaimer を一律で添える設計に統一されている（ホーム／パーツ提案／AIチャット／整備コメントの4か所で使用）
事業者は売り込まない問い合わせはユーザー起点のみ。事業者からのプッシュ型接触の実装は存在しない。未提携工場への関心は「需要蓄積」として貯め、営業に使う設計
情報はフラットに広告枠（isFeatured）は「広告」ラベルで明示される。shop_list_screen.dart に「ソート優先度を隠さない」と設計意図がコメントで残っている
撤退できる形で作るC2Cは削除ではなくフラグで凍結。地図はAPIキーが無ければ導線ごと隠してリストにフォールバック。止まっても壊れない作りになっている

4-3. コンセプトとコードがずれている点

ずれ①　パーツ提案が「理由の複数提示」の形になっていない

企画書は PartRecommendation のあるべき姿をこう定めている。

class PartRecommendation {
  final List<String> reasons;    // 推奨理由（複数）
  final List<String> cautions;   // 注意点・デメリット
  final int confidenceScore;     // 信頼度
  // ❌ "isBest" や "isRecommended" フラグは持たない
}

実際の実装（lib/models/part_listing.dart:416）はこうなっている。

class PartRecommendation {
  final PartListing part;
  final CompatibilityLevel compatibility;
  final String? compatibilityNote;   // ← 理由は1本の文字列
  final double relevanceScore;
}

「isBest を持たない」という禁止側は守られている。 だが「理由を複数」「注意点をセットで」という肯定側は、構造として存在しない。 比較のための材料が、ユーザーに1行しか渡っていない。 影響 差別化の中核である「当たり前の互換確認が不要」という体験が、 互換ラベル1つに縮んでいる。

ずれ②　ドライブマップが「Google Maps 標準」のまま

企画書は「Google Maps 標準だと『それでいい』で終わり、アプリの世界観・個性が死ぬ」として、 独自スタイルのビジュアルマップを目指すと明記している。実装は標準の Google Maps。 ただしこれは P3（優先度最低）として意図的に後回しにされたもので、判断としては筋が通っている。

ずれ③　仕様書が半年更新されておらず、現状と食い違っている

docs/FEATURE_SPEC.md の最終更新は 2026-02-21。 そこで「未実装（P0）」とされている車両マスタ・愛車タイムライン・ホームAI提案セクションは、3つとも実装済み。 ロードマップも「Phase 6 ← 今ここ（2026/Q1）」のまま止まっている。

リスク この文書を根拠に優先順位を決めると、済んだ仕事をやり直す。 8/25 の再監査が「文書を根拠にしない」と宣言したのは、まさにこれが原因である。

6バグ・不具合

6-1. 重大 iOS アプリが起動しない（白画面）

シミュレータで main() の1行目が例外を投げて止まる。UIが一度も描かれない。

Unhandled Exception: [core/duplicate-app] A Firebase App named "[DEFAULT]" already exists
  #2  main (package:trust_car_platform/main.dart:84:3)
ios/Runner/GoogleService-Info.plistlib/firebase_options.dart
Bundle IDcom.example.trustCarPlatform（Flutterのテンプレート既定のまま）jp.trustcar.app

firebase_core 4.9.0 は iOS でネイティブ側が先に plist から既定アプリを作るため、 そのあと Dart が別の設定で初期化しようとして衝突する。アンインストール後の新規インストールでも再現済み。

直せるのは人間だけ。 Firebase の iOS アプリは後から Bundle ID を変更できないため、 Console で jp.trustcar.app として新規登録し、plist を差し替える必要がある。 Android は 8/23 に同じ手当てを済ませてある。修正 PR #155 は 8/25 から4日間オープンのまま。

6-2. 重大・新規 main の iOS ビルドが失敗している

8/21 のレポートでは「iOS ビルドは main で成功している」と確認されていた。いまは失敗する。

cloud_firestore-6.4.1/ios/.../FLTPipelineParser.m:865:57: error:
  no visible @interface for 'FIRCollectionSourceStageBridge'
  declares the selector 'initWithRef:firestore:'
** BUILD FAILED **
ジョブ（main / f305f58 / 8-25）結果
Analyze & Test成功 解析・フォーマット・単体テスト・エミュレータ統合テストすべて通過
Storage & Firestore Rules Tests成功
Build Android成功
Build iOS失敗 上記コンパイルエラー

原因は依存の組み合わせで、アプリ側のコードではない。cloud_firestore 6.4.1 の ネイティブ実装が、CocoaPods が解決した Firebase iOS SDK のバージョンと噛み合っていない。 pubspec.yaml は cloud_firestore: ^6.1.2 と上限を開けているため、 解決されるバージョンが動くたびに再発しうる。

なぜ見逃されうるか。 build-ios は macOS ランナーの課金が10倍であることから、 main への push・手動実行・ios ラベル付きPR でしか走らない（意図した設計）。 通常のPRでは iOS は検証されない。ストア申請前のPRには必ず ios ラベルを付けること。
