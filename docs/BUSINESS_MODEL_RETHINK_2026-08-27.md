# ビジネスモデル再検討 — 「タカヤモーター自社の道具」として見る（2026-08-27）

**問い**（オーナーより）:

1. 本当に収益あるビジネスになるのか
2. 習慣として使ってもらえる機能やデータがそろっているか
3. それを使うことで、どんなメリットがあるか

**前提**: 外部に売る前に、**まず自社（タカヤモーター）の業務で元が取れるか**で見る。

---

## 0. 結論

**収益は出る。ただし「アプリを売って稼ぐ」のではなく「取りこぼしを減らして稼ぐ」形になる。**

コストが安すぎて、損益分岐が異常に低い。**年に1〜2台、車検の取りこぼしを防げば
それで元が取れる。** これは「アプリ事業として成立するか」より遥かに簡単な問いで、
答えは「する」。

ただし**いまのアプリでは、その1台を取り戻せない。** 理由は機能の不足ではなく、
**店が自分の顧客をアプリに載せる手段が無い**こと（§4）。ここが唯一にして最大の穴。

---

## 1. 前提を変えると、最大リスクが3つ消える

6月の事業性評価が「最大リスク」と呼んだものは、**外部に売る前提**から出ていた。
自社の道具として見ると、その大半が問題ではなくなる。

| 6月の最大リスク | 自社の道具として見ると |
|---|---|
| **2.1 ニワトリ・タマゴ問題**（工場とユーザーを同時に集められない） | **消える。** 工場は1社（自社）で確定。ユーザーは既存客に配る |
| **D-1 実在の工場データがゼロ**（実在店は1件のみ） | **消える。** 必要な工場は1件（自社）だけ。むしろ「1件しかない」が正しい状態 |
| **2.3 KYC不在**（工場の実在確認ができない） | **消える。** 自社なので確認は不要 |
| 2.2 B2BのROIを工場に証明できない | **消える。** 自分の売上を自分で見る。証明する相手がいない |
| 2.5 C2Cパーツ手数料8% | 不要。凍結のままでよい |
| 7.5 初期パートナー価格 | 不要。自社に価格を付ける意味がない |

**「捨てる勇気が事業性を決める」と6月の評価は締めていたが、
前提を自社に絞ると、捨てるまでもなく落ちる。**

## 2. 問い1: 本当に収益あるビジネスになるのか

### 2-1. かかる金（実測見積・`OPERATIONS_COST_ESTIMATE.md` / `SOFT_LAUNCH_COST_ESTIMATE.md`）

| 規模 | 月額 | 年額 |
|---|---|---|
| 10〜100人 | **約 ¥1,400〜1,800** | 約 ¥17,000〜22,000 |
| 1,000人 | 約 ¥4,170 | 約 ¥50,000 |
| 10,000人 | 約 ¥36,750 | 約 ¥441,000 |

地場の整備工場の顧客数は数百〜2,000台程度。全員が入れるわけではないので、
**現実的には 100〜1,000人の帯 = 年 ¥17,000〜50,000。**

内訳で効くのは Claude AI の従量課金（1,000人で月 $20.5）で、Firebase は誤差
（1,000人で月 $2.3）。**AI 機能を絞れば、さらに下げられる。**

### 2-2. 実数（2026-08-27 オーナー回答）

| 項目 | 値 |
|---|---|
| 車検1台あたりの粗利（法定費用を除く） | **2〜3万円** |
| 年間の車検台数 | **600台以上** |
| 車検案内（はがき・DM・電話）の年間費用 | **10〜30万円** |
| 年間の取りこぼし台数 | **把握できていない** |

### 2-3. 引き直した試算

車検は2年周期なので、**年600台 = 顧客の車両およそ1,200台**。
全員がアプリを入れるわけではないので、導入率を 30〜60% と置くと **360〜720人**。

```
 運用コスト     月 ¥3,000 前後（1,000人で ¥4,170 の帯）
                年 ¥36,000 前後

 車検1台の粗利  ¥25,000（2〜3万円の中央）
 ───────────────────────────────────────
 損益分岐       年 1.5台。実質「年2台」
```

**年2台取り戻せば元が取れる。年600台の 0.3% にあたる。**

戻る金は2本ある。

| 効き方 | 見込み | 根拠 |
|---|---|---|
| **案内費用の置き換え** | 年 **¥50,000〜150,000** | 年10〜30万円のうち、アプリが届く層（導入率50%想定）が置き換わる |
| **取りこぼしの回収** | 年 **¥150,000**（600台の1% = 6台 × ¥25,000） | 1%は控えめな見積もり |

```
 年間コスト   ¥36,000
 年間の効果   ¥200,000 前後（案内費用 + 取り戻し）
 ─────────────────────────────
 差引         年 ¥160,000 前後のプラス。投じた額の 5倍前後
```

**案内費用の削減だけでも、運用コストの1.4〜4倍。** 取り戻しがゼロでも赤字にならない。

### 2-4. いちばん重要なのは「把握できていない」という回答

**年間の取りこぼし台数が分からない、という状態そのものが問題。**

いまは分母が無いので、

- 何台逃しているのか分からない
- 手を打っても、効いたかどうか分からない
- 上の「年6台」も、当てずっぽうでしか置けない

**アプリを入れる最大の価値は、実は「取りこぼしが数えられるようになること」かもしれない。**

顧客の車検満了日がデータとして持てれば、

```
 3ヶ月後に満了を迎える顧客   ← リストが出る
 そのうち入庫した台数        ← 突合できる
 ─────────────────────────
 差分 = 取りこぼし           ← 初めて数字になる
```

**いま年20万円の効果と書いたが、それが正しいかを検証する手段が、いまは無い。**
アプリはその手段になる。ここは「収益」より前の話で、**経営の可視化**に近い。

## 3. 問い2: 習慣として使ってもらえる機能やデータがそろっているか

### 3-1. 測った結果（ペルソナに1年分を投入・2026-08-25）

```
 整備記録        733件 / 12ヶ月 / 10人
 ドライブログ    192件 / 12ヶ月 / 10人
 給油記録        機能が無い
```

**個人ユーザーがアプリを開く理由は、年に数回しかない。** 車検が2年に1回だから。
`docs/HABIT_DESIGN.md` に詳細。

### 3-2. だが、自社の道具なら要件が変わる

**顧客に毎日開いてもらう必要はない。** 必要なのは次の2つだけ。

| 必要なこと | いまの状態 |
|---|---|
| **アンインストールされないこと**（通知が届き続ける） | 弱い。開く理由が年数回だと消される |
| **車検の3ヶ月前に通知が届き、来店につながること** | 通知の仕組みはある |

つまり**「習慣」ではなく「生存」が要件**。毎日開かせる必要はないが、
**消されない程度には価値を感じてもらう必要がある。**

その観点で足りているもの・いないもの:

| | 状態 |
|---|---|
| 車検・点検リマインダー | **ある**（中核。これだけでも消されない理由になりうる） |
| 整備履歴が溜まる | **ある**（1年で数十件。乗り換えコストになる） |
| この1年のふりかえり | **ある**（2026-08-25 実装。年1〜2回、開きたい理由を作る） |
| 整備明細を店から送る | **ある**（ただし §4 の制約あり） |
| 給油記録 | **無い**。月2〜4回の接点を取り逃している |
| 出費カレンダー | **無い**（車検・保険・税金・タイヤの年間予定） |

**給油記録が無いのが最大の穴。** 唯一、月単位の接点を作れる行為。
入力3項目・20秒で、保存した瞬間に燃費が出る（毎回違う数字＝見たくなる）。

### 3-3. データはそろっているか

| データ | 状態 |
|---|---|
| 車種マスタ | **403車種・15メーカー**（2026-08-25 に 88→403 へ拡張。トラック34・バン32） |
| 用途区分（車検周期） | **自家用/貨物/軽貨物/事業用に対応**（2026-08-25 に登録画面へ配線） |
| 実在の工場データ | **1件（タカヤモーター）**。自社の道具としては、これで足りる |
| パーツデータ | **架空のまま**（`seed_parts.js` に明記）。正規品番は未取得 |
| 同車種の相場データ | 5車種のみ（`community_maintenance_trends`） |

**自社の道具として使う分には、車種マスタと車検周期がそろったので足りている。**
パーツと相場は、外部に売る段になってから。

## 4. 最大の穴 — 店が自分の顧客をアプリに載せられない

**これが唯一にして最大の問題。** コードを確認した結果:

```
 店 → 顧客の招待機能        無い
 店が顧客の車両を代理登録    無い
 店が顧客に整備記録を送る    あるが「問い合わせスレッド」が前提
```

整備明細を送る機能（`InquiryMaintenancePayload`）は実装済みで、店が明細を作り、
顧客が「記録に追加」で受け取れる。**しかしこれは、顧客が先にアプリを入れて、
自分から問い合わせを送ってきた場合にしか使えない。**

つまり現状の導線はこうなっている。

```
 顧客がアプリを見つける → 自分で入れる → 自分で愛車を登録する
 → 自分でタカヤモーターを探す → 自分で問い合わせる → やっと店とつながる
```

**既存客の大半は、この最初の一歩を踏まない。** 店側から「入れてください」と
渡す道具が無い。

### 直すなら

| 案 | 内容 | 大きさ |
|---|---|---|
| **A. 招待リンク／QRコード** | 店が顧客ごとに発行し、開くとタカヤモーターと紐づいた状態で始まる。車検証を撮れば愛車登録まで終わる | 中 |
| **B. 店による代理登録** | 来店時に店が車両を登録し、顧客はコードを入れて引き継ぐ。紙の顧客台帳からの移行もこれ | 大 |
| C. 車検証OCRだけで完結 | いまも可能だが、店とは紐づかない | 済 |

**A が現実的。** 車検の入庫時に「次回のご案内はこちらから」とQRを渡す運用に乗る。

## 5. 問い3: それを使うことで、どんなメリットがあるか

### 店（タカヤモーター）側

| メリット | 効き方 | いまの状態 |
|---|---|---|
| **車検の取りこぼしを防ぐ** | **これが本命。** 年1〜2台で元が取れる | リマインダーはある。ただし §4 で顧客に届かない |
| DM・はがきの削減 | アプリ通知が一部を肩代わり | 同上 |
| 顧客の車の情報が正確に分かる | 車検証OCRで型式・満了日が入る | ある（ただし release ビルドの日本語OCRは 8/25 に修正したばかり） |
| 整備履歴が店にも残る | 次回の提案材料。「そろそろタイヤです」が言える | ある |
| 問い合わせがアプリに集約 | 電話対応が減る。履歴が残る | ある（月次レポートも実装済み） |
| 顧客の囲い込み | 記録が溜まるほど他店に移りにくい | ある（1年で数十件） |

### 顧客側

| メリット | いまの状態 |
|---|---|
| 車検・点検を忘れない | ある |
| 整備の履歴が手元に残る（売るときに効く） | ある。**愛車カルテPDF も 8/25 にマージ済み** |
| 前回いくらかかったかが分かる | ある（この1年のふりかえり） |
| 同じ車種の人と費用を比べられる | ある（データは5車種のみ） |
| 給油・燃費の記録 | **無い** |

**顧客側のメリットが薄いと、消される。** 消されると店側のメリットも全部消える。
だから §3-2 の「生存」が店側の利益に直結している。

## 6. 判断と、やる順番

**結論: 自社の道具として見れば、収益は出る。障害は事業構造ではなく、
「顧客をアプリに載せる導線が無い」という一点。**

| # | やること | なぜこの順か |
|---|---|---|
| 1 | ~~実数を入れて試算を引き直す~~ **完了（§2-2〜2-4）**。年¥3.6万のコストに対し年¥20万前後の効果 | — |
| 2 | ~~店→顧客の招待導線~~ **完了（2026-08-28）**。店側の発行画面と顧客側の入力画面 | — |
| 3 | ~~給油記録~~ **完了（2026-08-28）**。入力4項目・保存した瞬間に燃費が出る | — |
| 4 | 出費カレンダー | 年間の出費見込み。開く理由を増やす |
| 5 | 外部への販売（他工場へ） | **自社で数字が出てから。** 「うちはこれで年◯台取り戻した」が最強の営業材料 |

**5 を先にやらないこと。** 6月の評価が「1商圏に集中」と言ったのは正しいが、
自社で効果が実証できていないものを他店に売るのは、順序が逆。

## 6-2. 実装して分かったこと（2026-08-28 追記）

### 招待コードは動く形になった

店側（`ShopInviteManageScreen`）でコードを発行し、顧客側
（`ShopInviteScreen`）で入れると、かかりつけとして紐づく。ルールは
Emulator で検証済み（140件パス）。

### 取りこぼしの可視化は、**データが取れない**

集計（`InspectionPipeline`）とカード（`InspectionPipelineCard`）は作ったが、
**店側の画面には配線していない。** 必要なデータが店から読めないため。

```
 取りこぼし = 満了を迎える台数 − 入庫した台数

 満了を迎える台数 ← 顧客の車両の「車検満了日」が要る
                    → firestore.rules は vehicles の read を
                      「本人」と「法人フリートのオーナー」に限っている。
                      **かかりつけの店は読めない。**

 入庫した台数     ← 顧客の整備記録が要る（同じく読めない）
                    またはお店側の基幹システムの入庫データ
```

**これは設計の穴ではなく、正しい制約。** 店が顧客の車のデータを丸ごと読めて
しまうほうが問題で、そこを緩めるのは筋が悪い。

### 直すなら（推奨は A）

| 案 | 内容 | 良し悪し |
|---|---|---|
| **A. 必要な値だけを顧客側が置く** | 顧客のアプリが、自分の `shop_customers` 文書に「次回の車検満了日」だけを書く。店はそれを読む | **車両の中身は見えない。** ルールも今のまま（本人だけが書ける）。実装は小さい |
| B. vehicles の read をかかりつけ店に開ける | ルールを1行足すだけ | **店が顧客の車の全項目を読める。** 走行距離も整備履歴も。やらないほうがいい |
| C. Cloud Functions で集計 | 顧客データに触らず、集計値だけを店に渡す | 正しいが、いちばん重い。件数が増えてからでよい |

A なら「顧客が同意して、店に伝える情報を最小限だけ渡す」形になり、
Trust という看板とも合う。

**入庫したかどうか**は、お店側が既に持っている情報（基幹システム・伝票）なので、
突き合わせは手作業からでも始められる。まず「満了を迎える台数」が出るだけでも、
いまの「把握できていない」よりは前に進む。
