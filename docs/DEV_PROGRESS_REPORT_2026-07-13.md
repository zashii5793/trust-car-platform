## エグゼクティブサマリー

Trust Car Platform は **「自動車の整備・点検履歴を確実に管理し、所有のライフサイクル全体（購入前〜整備〜売却）を支える」** ことを North Star に据えた Flutter + Firebase 製アプリ。開発開始（2026-02）から約5か月で、**コア機能（車両管理・整備履歴・車検リマインダー）は実装完了**し、現在は **B2B（整備工場向け）収益化・コミュニティ・差別化機能（愛車カルテ／メンテ予測）** のフェーズに入っている。

| 指標 | 現状 |
|------|------|
| 開発期間 | 2026-02-04 〜 現在（約5か月・184コミット） |
| コード規模 | Dart 357ファイル / 約133,000行（lib + test） |
| 実装レイヤー | Service **51** / Provider **18** / Model **33** / Screen **52** |
| テスト | **154ファイル / 約3,400件超**（`--exclude-tags emulator` 全パス） |
| Firestoreルール | 710行 / 複合インデックス 42本 |

**総評**: 技術的な作り込み（アーキテクチャ・テスト・品質）は非常に健全。一方で **「作ったものが本番ユーザーに届いていない」構造的ボトルネック**（未マージPRの滞留・本番デプロイ/実機投入の人間タスク未完）が最大の課題。プロダクトは「実装フェーズ」から「リリース・検証フェーズ」への移行が必要な段階にある。

## 1. 開発の全体像

### 1.1 アーキテクチャ（確立済み・安定）

```
main.dart → Injection.init() → ServiceLocator
                                    ↓
Provider（コンストラクタ注入） ← Service（Result<T, AppError>）
    ↓                                ↓
  UI層（screens/）              Firebase SDK
```

- **Service層に Firebase 操作を集約**（51サービス）。全メソッドが `Result<T, AppError>` パターンで統一。
- **DI は ServiceLocator**、Provider はコンストラクタ注入。方針が全コードで徹底されている。
- **TDD（RED→GREEN→REFACTOR）** をルール化し、Service追加時のエッジケース（空値/境界値/存在しないID/権限違反）を必須化。

### 1.2 主要依存パッケージ

Firebase フルスタック（Auth 6 / Firestore 6 / Storage 13 / Messaging / Crashlytics / Performance / Analytics / Remote Config）、`provider`、OCR（`google_mlkit_text_recognition` + `camera`）、PDF出力（`pdf` + `printing`）、位置情報（`geolocator`）、課金（`purchases_flutter` = RevenueCat）。**本番運用に必要なSDKは一通り導入済み。**

## 3. 品質状況

- **テスト**: 154ファイル・約3,400件超。Service 51ファイル / Screen 43ファイル / Provider 17ファイルを網羅。ウィジェットテスト・golden・Firestoreルールテスト（JS）・統合テストを含む多層構成。
- **静的解析**: `flutter analyze lib/` クリーンを継続維持。`dart format` を CI 同条件で強制。
- **CI**: GitHub Actions で Analyze & Test / Firestoreルールテスト / Android・iOS ビルドを自動実行。直近のナイトブランチはCI全GREEN。
- **セキュリティ**: Firestoreルール710行・42インデックスをリポジトリ管理。新規コレクション追加時にルール同時定義を徹底。シークレットのハードコード禁止を規約化。

**品質面のリスクは低い。** 自動テスト・静的解析・CIの三層で回帰を抑止できている。

## 4. 現状の課題（重要）

### 🔴 課題1: 未マージPRの滞留 — 最大のボトルネック

**CI GREEN のまま未マージの Pull Request が 20件超**（多くが draft）。うち **priority: high の Issue を解決するもの**が含まれる:

- PR #68 — 愛車タイムライン マイルストーン（Issue #62 close）
- PR #78 / #67 — AIメンテ予測提案の強化（Issue #63 close）
- PR #74 → #75 → #76 — 整備記録の検証フィールド＋工場裏書きバッジ（moatの中核・依存順あり）
- PR #69 — 愛車カルテPDF、PR #73 — 整備記録の解説機能MVP

**影響**: 実装は完了しているのに **main に取り込まれず、プロダクトに反映されていない**。「夜間自律開発で機能を積み上げる → 人間のマージが追いつかない」構造。マージ順序の依存関係（例: #74→#75）も滞留を助長。

**推奨**: レビュー/マージのバッチ処理デーを設ける。依存関係のあるPR群（車歴検証系 #74/#75/#76）を優先的に順序マージ。

### 🔴 課題2: 本番リリースをブロックする「人間タスク」未完（Issue #49・priority: high）

コード実装は済んでいるが、AIでは代替不可の設定作業が未了で **実機で1台も車両登録できない状態**:

- Firebase Authentication の有効化（🔴 最優先）
- Firestore/Storage ルールの本番デプロイ（`firebase deploy`）
- `google-services.json` / `GoogleService-Info.plist` の配置
- Cloud Storage の有効化

**影響**: プロダクトが「動くコード」であって「使えるサービス」になっていない。実ユーザー検証（PMF確認）が始められない。

### 🟠 課題3: 開発環境に Flutter SDK が無い（自律セッションの制約）

クラウド/夜間セッションはネットワーク制限で Flutter を安定導入できず、検証をCIに委譲するケースが常態化。ローカルでの `flutter test`/`analyze` が回らないため、フィードバックが1サイクル遅い。

### 🟠 課題4: 集客エンジン（GoogleMap連動）の外部API依存（Issue #41/#43/#44）

ニワトリ・タマゴ問題を需要側から割る「GoogleMap風の網羅表示＋提携フリーミアム」は設計合意済み（`BUSINESS_VIABILITY_ASSESSMENT.md §7.7`）だが、**Google Maps / Places API キーの発行・課金設定（人間タスク #17）待ち**。Phase2（需要蓄積）はPR #78で先行実装済み、Phase1（地図描画）が未着手。

### 🟡 課題5: UI一貫性の技術的負債（Issue #29/#30）

- ダークモード非追従の `Colors.*` 直書きが残存（→ `AppColors` へ段階統一中、PR #53/#57 で対応中）
- 共通UIコンポーネント（`AppButton`/`AppTextField`/`AppDialog`）の採用率が30〜40%（→ #54 で `AppDialog` 統一フェーズ1着手）

いずれも回帰リスク管理のためファイル単位で分割対応中。**機能ではなく磨き込みの負債**であり、優先度は中。
