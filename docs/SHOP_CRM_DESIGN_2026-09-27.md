# 店の顧客台帳と、車の記録の共有（設計）

**作成**: 2026-09-27
**ブランチ**: `claude/model-cost-report`

## 1. 出発点

同じ1台の車でも、見ている人によって別のものに見える。

| 見る人 | 見えているもの | 持ち主 |
|---|---|---|
| ユーザー | **自分の車**。走った距離、かけたお金、次にやること | ユーザー |
| 整備・修理の店 | **お客さんと、その車**。次の車検、最後に来た日、声をかける時期 | 店 |

これを1つのデータに押し込むと、どちらかの都合が崩れる。

- ユーザーのデータを店に開けると、走行距離も整備履歴も全部渡ってしまう
- 店の台帳をユーザーの記録から作ると、**アプリを入れていない客は台帳に載らない**

**だから別々に持ち、ユーザーが同意したときだけつなぐ。**

## 2. 今の作りで足りないところ（2026-09-27 実測）

| 問題 | 中身 |
|---|---|
| 店が顧客を登録できない | `shop_customers` はユーザーが招待コードを入れたときだけ作られる。ルールが店からの書き込みを禁じている |
| 全件読み | `ShopInviteService.customersOf()` が顧客を全件取得する。画面を開くたびに顧客数ぶん読む |
| 1店＝1アカウント | `shops/{shopId}` の docId が店主の uid。スタッフが複数いる店・複数店舗の会社を表せない |
| 法人 | 顧客1人＝1ドキュメント。法人が数十台持つ形を表せない |
| 共有 | `VehicleHistorySharingService` はあるが、どの画面からも呼ばれていない |
| ~~一覧の穴~~ | `shop_customers` と `vehicle_sharing_permissions` の `list` が認証だけで通っていた。**2026-09-27 に修正** |

## 3. 規模の前提

最初の本番の店は、**法人リースが約100社、個人が約4,000人**の顧客を持つ。
設計の目標は、1店あたり次の規模で遅くならず、読み取り料金も膨らまないこと。

| 項目 | 目標 |
|---|---|
| 顧客 | 5,000件 |
| 車両 | 10,000台（法人が1社で数十台持つ） |
| 整備実績 | 年 20,000件 |
| スタッフ | 数十人 |

**守るルール**:

- 一覧は**20件ずつ**読む（カーソルで続きを取る）。全件は読まない
- 件数は `count()` の集計クエリで出す（4,000件読まずに「4,000名」を出す）
- 並べ替えと検索は、Firestore のインデックスで引ける形にしておく

## 4. データの形

### 4-1. 店のメンバー

```
shops/{shopId}/members/{uid}
  role: 'owner' | 'staff'
  displayName
  addedAt
```

ルールの判定は `isShopMember(shopId)`（このドキュメントがあるか）。
既存の「docId == 店主の uid」は、店主を最初の owner として移す。

### 4-2. 顧客（店の台帳）

```
shops/{shopId}/customers/{customerId}
  kind: 'individual' | 'corporate'
  name, nameKana
  searchKey          // 検索用。カナをひらがな・全角半角・空白を正規化したもの
  phone, email, postalCode, address
  externalId         // 整備管理ソフトの顧客番号。取込のやり直しで二重にしない
  vehicleCount
  nextInspectionAt   // 持っている車のうち、いちばん近い車検満了日
  lastVisitAt
  linkedUserId       // アプリのユーザーとつながっていれば
  tags, note
  source: 'manual' | 'csv' | 'invite'
  createdAt, updatedAt
```

### 4-3. 顧客の車両（店の台帳）

顧客の下にぶら下げず、**店の直下に平らに置く**。
「今月車検の車」を顧客をまたいで満了日順に出すため（サブコレクションだと店全体で並べられない）。

```
shops/{shopId}/customer_vehicles/{vehicleId}
  customerId
  plate, plateKey    // ナンバー。検索用に正規化
  maker, model, year, modelCode, vin
  inspectionExpiry
  lastVisitAt, lastMileage
  linkedVehicleId    // ユーザーのアプリの車両とつながっていれば
  externalId
```

### 4-4. 整備実績（店の台帳）

```
shops/{shopId}/service_records/{recordId}
  customerId, customerVehicleId
  date, mileage, type
  totalCost, partsCost, laborCost, miscCost, taxAmount
  maker, model, year  // 車種レポートの集計用に写しておく
  sentRecordId       // ユーザーに明細を送った場合、その整備記録のID
  externalId
```

## 5. 画面

### 店側：顧客台帳

- 上部に件数（個人／法人／アプリ利用中）。`count()` で出す
- タブ：**顧客** ／ **車両（車検の近い順）** ／ **しばらく来ていない**
- 検索：名前（カナ）・ナンバーの前方一致
- 20件ずつ。下までスクロールしたら次の20件を読む
- 顧客詳細：車両・整備実績・メモ。ここから「このお客さん用の招待コード」を出せる

### ユーザー側：新しい店に共有する

§7 を参照。

## 6. 台帳とアプリをつなぐ

1. 店が顧客詳細で**その客専用の招待コード**を出す（`shop_invites` に `customerId` を持たせる）
2. 客がアプリでコードを入れる → 既存の `shop_customers/{uid}` に `customerId` が入る
3. 店の台帳は `shop_customers` を見て「アプリ利用中」を表示する

**ユーザーが店の台帳に書くことはない**し、**店がユーザーの車両を読むこともない**。
つながりは `shop_customers` という「ユーザーが置いた札」1枚だけで表す。

## 7. ユーザー → 新しい店への共有

初めて行く店に「この車のこれまで」を渡す機能。
今は、店を替えると履歴がゼロからになる。

**形：写しを渡す（カルテを手渡しするイメージ）**

```
shops/{shopId}/shared_vehicles/{shareId}
  ownerId, vehicleId
  vehicle: { maker, model, year, plate?, mileage, inspectionExpiry }
  records: [ { date, type, title, cost, mileage, shopName } ]   // ユーザーが選んだ分
  sharedAt, expiresAt
```

- 書けるのはユーザーだけ。店は読むだけ
- **ユーザーが中身を選ぶ**（ナンバーを出すか、どの記録を渡すか）
- 期限つき（既定30日）。ユーザーはいつでも取り消せる（ドキュメントを消す）
- 店は「この写しから台帳に登録」できる

**生きたデータを開けない理由**: `vehicles` と `maintenance_records` を店に開けると、
ルールで「この店に許可があるか」を毎回引く必要があり、一覧のクエリで判定できない。
しかも、取り消したあとに店の手元に何が残ったかが分からなくなる。
写しなら「何を、いつ、どこに渡したか」がはっきりする。

既存の `vehicle_sharing_permissions` は使っていないので、この形に置き換える。

## 8. 車種別の維持費レポート

### 何を出すか

「Mini クーパーを買ったら、年にいくらかかるか」。

- 年間の維持費（中央値と、ばらつきの幅）
- 内訳：車検1回あたり／車検以外の整備／燃料
- 車の年数ごとの推移（3年目・7年目・10年目でどう変わるか）
- よくある整備（何を、どのくらいの頻度で）

### どこから集めるか

1. アプリ利用者の整備記録と給油記録
2. **店の整備実績**（§4-4）。顧客が何千人といる店が1つ入るだけで、初日から数字が出る

**ユーザーの入力を待たずに価値が出る**。自分の記録が溜まる前から
「同じ車の人はこのくらい」が見えるので、使い始めの半年で離れる理由を減らせる。

### 守ること

- **5台未満（持ち主が5人未満）の車種は出さない**。個人の数字が特定されるため。
  その場合は「メーカー全体」に広げて出す
- 1社が同じ車種を何十台も持っていると、その会社の数字になってしまう。
  **持ち主（顧客）単位で数える**
- 集計はサーバー（Cloud Functions）で毎晩。アプリからは書かせない
- 規約に統計利用の条項が要る（ユーザー向け・店舗向けの両方）

### 既存の `community_maintenance_trends` について

アプリからの書き込みがルールで拒否され、エラーも握りつぶしていたため、
**本番で1件も集まっていない**（中身はシードの推定値だけ）。
「中央値」と名乗っているが、実装は平均。台数も記録1件ごとに増えていた。
新しい集計に置き換える。
