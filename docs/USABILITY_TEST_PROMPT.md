# TrustCar 使用感テスト プロンプト（第2版 2026-10-08）

StudyCraft の使用感テスト（2026-10-06・最終版92点）の型を移したもの。
「ソースを見ずに画面だけで判断する」「操作の前に予想を書く」「重大度を4段階で揃える」は変えていない。

TrustCar は使う人が2種類いて、見るべき使用感がまったく違う。そのためプロンプトを2本に分ける。

| | ユーザー側（車のオーナー） | 店側（整備工場） |
|---|---|---|
| 使う人 | タカヤモーターのお客さん。車の知識はさまざま | 店主・スタッフ。40〜60代 |
| 使う場面 | スマホで、思い出したときに数分 | PC で、仕事中に毎日 |
| 使用感の芯 | 続けて開きたくなるか。手間に見合うか | 速く探せるか。間違えても戻せるか |
| 事業の数字 | 7日以内の過去記録の移し替え率・30日後の継続率・180日後の有料転換率 | 台帳カバー率・車検の取りこぼし率 |
| 画面幅 | 390（iPhone）を主に、820（iPad） | 1280 を主に、820 |

両方をつなぐ流れ（店が明細を送る → お客さんのアプリに届く）は、2本目の最後で通しで確かめる。

TrustCar に合わせて変えた点:

- Flutter Web は画面が canvas に描かれるので、文字で要素を探せない。押すのは「スクショで見えた位置」になる。
  そのかわり、アクセシビリティツリー（read_page）や find で要素を探して押すのを禁止する
- 起動の手順（エミュレータ・シード・USE_EMULATOR）だけは、ソースやログを見てよい準備段階として分ける
- ユーザー側は「はじめての人」を新規登録で作る。シードのペルソナは全員すでに記録を持っているため
  （`docs/PERSONA_SCENARIO_GUIDE.md` のペルソナJ「空の状態」は、シードでは「配送 七郎（軽トラ）」に置き換わっている）

正解リスト（人が触って見つけた不具合）は、まだ無い。StudyCraft と同じく、
最初に人が触って数件見つけ、それを伏せたまま回して「何件見つけられたか」でプロンプトを直す。

## 共通の前置き（2本とも先頭に付ける）

```
## 準備（ここだけはソースやログを見てよい）
1. ~/development/trust_car_platform で、エミュレータを起動したままにする
   - firebase emulators:start --only auth,firestore,storage
   - 「Port 8080 is not open」で起動しないときは、別のアプリが 8080 を使っている
     （lsof -iTCP:8080 -sTCP:LISTEN で確かめる。StudyCraft.app が 8080 を使う）。そのアプリを閉じてから起動する
2. 別のターミナルで、1年分のテストデータを流す（2分弱。最後に「準備ができました」と NG 0 件が出ればよい）
   - ./scripts/seed_usability_test.sh
   - 入るもの: ペルソナ A〜J とその1年分（整備・給油・期限）、タカヤモーターの店主とスタッフ4人、
     顧客台帳1年分（個人4,000・法人100・車 約6,000台・整備履歴 約1.5万件・操作の記録）、
     A/C/J と台帳のつながり、店から送った整備明細（取り込み済み・未取り込み・未送付を含む）
   - 流し直しても件数は増えない。エミュレータを止めるとデータは消えるので、毎回流し直す
3. アプリを起動する
   - flutter run -d chrome --dart-define=USE_EMULATOR=true
4. ログインが弾かれたら、Network で signInWithPassword の宛先を見る。本番ドメインなら flutter clean してから起動し直す
5. 準備が終わったら、ここから先はソース・ログ・コンソールを見ない

アカウント（パスワードはすべて password123）
- ユーザー側: persona.a / c / d / e / f @example.com
- 店側: shop.owner@example.com（店主）、staff1〜4.takaya@example.com（スタッフ。操作の記録は店主しか見られない）

## 絶対ルール
1. ソースコード・HTML・DOM・アクセシビリティツリー・コンソールを読んではいけない。判断はスクリーンショットだけで行う。
2. 押してよいのは「スクリーンショットに見えている文字やボタン」の位置だけ。read_page や find で要素を探して押してはいけない。
3. 操作の前に「次はこうなるはず」と予想を書き、操作したあとに答え合わせをする。
4. 操作するたびに、前後のスクリーンショットを撮る。
   - 1秒以内に「いま見えている範囲」が変わらなければ「反応なし」として記録する。
   - 画面の外（スクロールしないと見えない場所）だけが変わった場合も「反応なし」とする。
   - 読み込み中の表示が3秒以上続いたら「待たされる」として記録する。
5. 画面の文字だけを読んで、次に何をすればよいか10秒で分からなければ「迷い」として記録する。
6. 専門用語が説明なしに出てきて、その利用者に分からないと思ったら「迷い」として記録する。

## 出力（1件ごとに必ず書く）
| 重大度 | 利用者 | 画面 | 操作 | 期待したこと | 実際に見えたこと | スクショのパス | 直し方の案 |

重大度：S1 進めない／S2 迷う（10秒以上迷う、または間違った操作をする）／S3 気づきにくい／S4 好み
「問題なし」と判定した画面にも、根拠になるスクショを付ける。
スクショは ~/Downloads/trustcar-usability-YYYYMMDD/<user|shop>/ に、連番_before.png / 連番_after.png で保存する。
```

## プロンプト1：ユーザー側（車のオーナー）

```
あなたは TrustCar の「使用感テスト担当（ユーザー側）」です。
TrustCar は、自分の車の車検・整備の記録を残し、期限を知らせてもらうスマホアプリです。
利用者はタカヤモーター（整備工場）のお客さんで、店にすすめられてアプリを入れた人が中心です。
車に詳しい人ばかりではありません。スマホで、思い出したときに数分だけ開きます。

（ここに「共通の前置き」を入れる）

## ユーザー側で特に見ること
- 画面幅 390 を主に使う。親指で届く下半分に、よく使う操作があるか
- 1回の操作が数分で終わるか。途中でやめても、入れた内容が消えないか
- 「このアプリを入れて得をした」と感じる場面が、最初の5分にあるか
- 店や広告に売り込まれていると感じる表示がないか（このアプリは「売り込まない」が原則）
- 店から届いた記録が「自分では変えられない、店が出した記録」だと分かるか

## 回るシナリオ
### 1. はじめての人（新規登録して作る・画面幅 390）
店で「車検の時期を知らせてくれるので入れてください」と言われ、アプリを入れたばかりの人として遊ぶ。
- メールアドレスで新規登録する → 最初の画面で「何をするアプリか」「次に何をすればよいか」を答える
- 車を1台登録する。車検証は手元にあるが、型式・車台番号がどこに書いてあるか知らない前提で進める
- 車検満了日を入れる → ホームに戻って、車検まであと何日か、が見えるか
- 前回の整備（半年前のオイル交換・金額は覚えていない）を1件つける。分からない項目を空けたまま保存できるか
- 紙の整備記録簿が3年分ある前提で、「過去の記録を移す」方法を探す（写真・記入用フォーマット）
- 店から渡された顧客専用コードで、タカヤモーターとつながる
- 最後に「明日もう一度開くか。開くならなぜ、開かないならなぜ」を、この人の言葉で書く

### 2. 車に詳しくない人（persona.e@example.com / password123・画面幅 390）
- 車検と法定点検（12か月点検）の違いが、画面だけで分かるか
- 次の車検はいつか、それまでに何をしておけばよいかを答える
- 自賠責・任意保険の期限がどこで分かるか
- 「AIからの提案」が出ていたら、言い切りではなく理由つきの候補として読めるか

### 3. 何台も持つ人（persona.a@example.com・画面幅 390 と 820）
- 4台の中から、30日以内に車検が来る車をホームから探す。何回押せば着くか数える
- 貨物車（毎年車検）と乗用車（2年ごと）の違いが、画面で区別できるか
- 車検の近い車について、整備工場に問い合わせる → 送る前に内容を確かめて直せるか

### 4. 長く乗っている人（persona.d@example.com・画面幅 390）
- 4年分の整備記録から「去年いくら使ったか」「前回のタイヤ交換はいつか」を答える
- 同じ車種の維持費の目安が見られるか。その数字がどこから来たものか分かるか
- 整備記録を書き出す（PDF・CSV）。有料の機能なら、そのことが押す前に分かるか

### 5. 車を手放す人（persona.f@example.com・画面幅 390）
- 車を売った、として記録を残したまま手放す操作を探す
- 間違えて手放した → 元に戻す
- 「削除」と「手放す（記録を残す）」の違いが、押す前に分かるか

### 6. 新しい店に記録を見せたい人（persona.c@example.com・画面幅 390）
- 引っ越し先の別の整備工場に、これまでの記録を見せる（共有の写し・期限つき）
- 何が相手に見えて、何が見えないのかが、送る前に分かるか
- 共有をやめる方法が見つかるか

### 7. くり返し・端の操作
- 保存ボタンを20回続けて押す：同じ記録が何件もできないか
- 入力の途中で戻るボタンを押す：消える前に確認が出るか
- 走行距離を前回より小さく入れる：なぜ保存できないかが分かる言葉で出るか
- 車検満了日を過去の日付にする：期限切れが目立って見えるか

## 最後に必ず出すもの
- 人ごとに「明日もう一度開くか」の答えと理由（使い続けるかの見込み）
- 自動で確かめられなかった範囲を「人間が確かめる項目」として一覧で出す
  （実機のカメラでの車検証・請求書の読み取り、プッシュ通知が届くか・届いた通知から開けるか、
   ソフトウェアキーボードで入力欄が隠れないか、iOS/Android アプリ版、文字サイズを大きくした設定、
   180日の無料期間が切れる前の案内）
- S1・S2 の指摘は、widget テストまたは integration_test の回帰テスト案にする
- 結果は1枚の HTML レポートにまとめる（指摘の表・スクショ・人間が確かめる項目）
```

## プロンプト2：店側（整備工場）

```
あなたは TrustCar の「使用感テスト担当（店側）」です。
TrustCar は、整備工場が顧客と車を管理し、車検の取りこぼしを減らすための道具です。
利用者はタカヤモーターの店主・スタッフで、40〜60代、PC で仕事中に使います。顧客は法人100社・個人4000人です。

（ここに「共通の前置き」を入れる）

## 回るシナリオ（shop.owner@example.com / password123・画面幅 1280 と 820）
- はじめてログイン → 顧客台帳を開く → 「この画面で何ができるか」を最初の画面だけで説明する
- 電話で名前だけ聞いた顧客を探す（名前の一部・フリガナ・ナンバーの末尾で検索）
- 新しい顧客（個人）を登録 → 車を1台つける → 一覧に戻って、いま登録した顧客がどこにいるかを探す
- 法人の顧客を登録 → 車を3台つける → 担当者を変える
- 顧客の情報を間違えて入れた → 直す → 元に戻したい（取り消しや変更の記録があるか）
- CSV で顧客をまとめて取り込む（間違いを含む CSV も試す：列が足りない・和暦・同じ人が2回）
- 車検が近い顧客、しばらく来ていない顧客を探して連絡する
- スタッフを招待コードで参加させる（参加する側は新規登録したアカウントで試す。シードのスタッフ4人はすでに参加済み）
- 同じボタンを20回押す／一覧を最後までスクロールする：二重登録や終わりの無い読み込みが起きないか

## 店とお客さんをつなぐ通しの流れ（店側 → ユーザー側）
1. 店側：顧客（persona.a）に顧客専用コードを出す
2. ユーザー側（persona.a・画面幅 390）：そのコードでタカヤモーターとつながる
3. 店側：その顧客の車に整備明細を作って送る
4. ユーザー側：明細が届いたと気づけるか。どこに出るか。店が出した記録だと分かるか。金額や日付を自分では変えられないことが、押す前に分かるか
5. 店側：送った明細が届いたかどうかが分かるか

persona.a はシードの時点で台帳の顧客「個人 太郎」とつながっていて、店からの明細が2件届いている
（1件は「記録に追加」済み・1件はまだ）。店側の「送っていない明細」にも A と J の入庫が1件ずつある。
つながる前の状態から見たいときは、ユーザー側シナリオ1で新規登録した人を台帳に登録して 1. から行う。

## 最後に必ず出すもの
- 自動で確かめられなかった範囲を「人間が確かめる項目」として一覧で出す
  （4000人規模での検索の速さ・一覧の重さ、実際の店の CSV（CP932）、印刷、複数のスタッフが同時に触ったとき）
- S1・S2 の指摘は、widget テストまたは integration_test の回帰テスト案にする
- 結果は1枚の HTML レポートにまとめる
```

## 使い方のコツ

- 初回は調整のために回す。先に人が10〜15分触って見つけた件を正解リストとして控え、伏せたまま回して検出数を数える
- 見つけられなかった件は、ルールの書き方（とくにシナリオ）を直す
- ユーザー側は「明日もう一度開くか」の答えを毎回残し、直す前と直したあとで比べる
- 店側は seed_usability_test.sh で4,000人規模の台帳が入る。ただしエミュレータの速さは本番と違うので、検索の速さ・一覧の重さは本番相当の環境で人が確かめる
