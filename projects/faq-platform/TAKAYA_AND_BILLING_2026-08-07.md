## 2. 課金プランと価格 — 社内資料が食い違っています

### 発見: 月額が2〜3倍ずれています

```
 出所                                    月額              初期費用
 ─────────────────────────────────────  ───────────────  ──────────────────
 ROADMAP.md:150（Task 3.2 Stripe連携）    ¥100,000/月想定   記載なし
 ROADMAP.md:17（全体方針）                月¥10万 × 10社    ―
 docs/billing_design.md                  〇〇/△△/□□      〇〇,000 円
                                          （プレースホルダ）
 Drive「A社 本番導入計画」（初版）          ¥30,000〜50,000   ¥50,000〜100,000
 Drive「A社 本番導入計画 v2」              「案件ごとに設定」  「案件ごとに設定」
```

**ROADMAP の月10万円と、Drive の導入計画の月3〜5万円は、2〜3倍違います。**

これは「未確定だから幅がある」のではなく、**別々の文書が別々の前提で書かれている**
状態です。ROADMAP は「月¥10万 × 10社 = 月100万」を最初のマイルストーンに置いており、
この数字が変わると**収益計画そのものが変わります。**

```
 月10万 × 10社 = 月100万   ← ROADMAP のマイルストーン
 月 4万 × 10社 = 月 40万   ← Drive の導入計画の水準で計算し直すと
```

> **ご判断いただきたいのは「いくらにするか」の前に、
> 「どちらの数字で営業してきたか」です。** 既に提示済みの金額があるなら、
> そちらが事実上の基準になります。

### プラン設計そのものは完成しています

`docs/billing_design.md`（256行）は、価格以外は作り込まれています。

```
 プラン              APIキー           月額固定   API実費              上限
 ─────────────────  ───────────────  ────────  ──────────────────  ────
 A. 包括            運営マスターキー   〇〇円     含む（上限内）        あり
 B. 実費連動        運営の子キー       △△円     顧客実費 ×(1+手数料Y%)  なし
 C. BYO            顧客自身のキー     □□円     顧客が直接支払い      なし
```

設計書には、実務で効く細部まで入っています。

```
 ・USD建て請求の換算レート → 「月末TTM」と契約書に明記すれば揉めない（:228）

 ・営業向けのプラン提示テンプレート（§5）
```

**したがって「価格を決める」以外に開発待ちの設計作業はありません。**

## 3. 「ROADMAP通り2社目まで待つか」

### ROADMAP の規定

```
 ROADMAP.md:36-37
 ### Phase 3: SaaS化・課金（〜2ヶ月）🟢収益化
 2社目契約のタイミングで実装。

 ROADMAP.md:228（やってはいけないこと）
 ❌ Phase 1飛ばしてSaaS化に進む（信頼性ゼロでB2B契約は取れない）

 ROADMAP.md:18-19（先行事例）
 - 第1号：デモ会社（無料運用 → 事例化）          ← タカヤモーター
 - 第2号：導入企業（有料契約のテストケース、教育業界） ← A社
```

### 発見: 2社目は既に本番稼働しています

Drive の「A社 導入完了報告書」（2026-06-17 作成）に、次の記載があります。

```
 状態: ✅ 本番稼働開始
 対象: Inquira (社内 FAQ AI プラットフォーム)
 構成: オンプレ Windows Server + IIS リバプロ (HTTPS) + Google OAuth
```

**ROADMAP が「第2号：導入企業（有料契約のテストケース、教育業界）」と定義した相手が、
2026-06 の時点で本番稼働に入っています。**

> ※ 顧客のFQDN・IPアドレス・証明書情報などは、`CHANGELOG.md:165` が
> 「営業/顧客獲得系ドキュメントを `.private/` に隔離」としている方針に沿って
> 本書には転記していません。

### したがって、待つ対象が既に無い可能性が高いです

```
 ROADMAP の着手条件      「2社目契約のタイミング」
 実態                    2社目は 2026-06 に本番稼働開始
 ─────────────────────  ──────────────────────────────────
 帰結                    条件は既に満たされている……ただし1点を除いて
```

### 残る唯一の不確定 — 「契約」が締結されたか

ROADMAP の条件は「2社目**契約**」であって「2社目**稼働**」ではありません。

Drive の「A社 本番導入計画 v2」（2026-06-02）では、**契約・料金が未確定**でした。

```
 検討1: 契約形態と料金   🔴 最優先   ← 「残る検討事項3項目」の筆頭
 タスク1  本契約書ドラフト作成・送付   🔴 最優先
 タスク3  契約締結・印鑑回収           🔴 最優先
```

その2週間後の導入完了報告書には**稼働開始**は書かれていますが、
**契約締結の記載は見当たりませんでした。**

```
 □ A社との有料契約は締結済みか、それとも稼働だけ先行しているか
```

**これが埋まれば判断は自動的に決まります。**

```
 締結済み  → ROADMAP の条件は満たされている。待つ理由は無い
             → Phase 3 着手は「前倒し」ではなく「予定どおり」
 未締結    → 条件未達。3.2-a（メータリング）のみ着手し、残りは待つ
             → ROADMAP:228 の禁止事項には触れない（Phase 1 は飛ばさないため）
```

### 補足 — ROADMAP の記述はもう1箇所古くなっています

```
 ROADMAP.md:44  Task 1.1 現状：HashEmbedding（ランダムに近い精度）
 実態            TF-IDF と sentence-transformers 系の2バックエンドが実装済み
                （app/rag.py / app/config.py:47 のデフォルトが "tfidf"）
```

PR #114 が既に指摘済みですが、**ROADMAP 自体は更新されていません。**
Phase の判定に ROADMAP を使うなら、この鮮度の問題は課金判断にも効きます。
