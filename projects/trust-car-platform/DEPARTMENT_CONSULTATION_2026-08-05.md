## 2. 4部署が一致した点（＝論点ではなく、事実として扱ってよい）

**誰も反対しなかった、部署をまたいで独立に同じ結論に達した点は3つです。**

### 一致① 詰まっているのは開発側ではなく、人間しかできない作業

- 開発「実装は全件パス・analyzeクリーン。詰まりは未デプロイのルール/インデックスとストア審査という人間側にある。**開発側の効率化施策はリードタイムを1日も縮めない可能性が高い**」
- データ「本番に実デプロイ済みのルールが取れるまで、デプロイ可否は判断材料が無い」
- QA「テストは緑だが本番は未検証」

裏付け（週次PMレポート #112、本日自動生成）:

| 指標 | 値 |
|---|---|
| テスト | ✅ 3000件パス / 0件失敗 |
| 静的解析 | ✅ No issues |
| `google-services.json`（Android） | ❌ **未配置** |
| `GoogleService-Info.plist`（iOS） | ❌ **未配置** |
| HUMAN_TASKS.md | 📋 **29件残り（完了 0件）** |

> **完了0件。** これが最も重い数字です。AI側の生産量をどれだけ上げても、この29件が0のままなら本番には何も届きません。

### 一致② 「反応がなければ凍結」の判定基準が言語化されていない

4部署すべてが独立に指摘。開発「何社に当てて何件反応か、いつまでか」／データ「フリート登録・メンバー招待・CSV出力・レポート閲覧が**一切計測されていない**（`analytics_service.dart` のイベントはB2C前提のみ）」／UI・UX「期限・閾値が示されていない」／QA「凍結の瞬間に判断者がいなくなる」。

> データ部門の指摘が決定的です。**現状の計測では「B2Bで反応がない」を数字で言うことができません。** 凍結judgmentの根拠が取得不能な状態です。

### 一致③ 効率化＝削除・整理に踏み込むと不可逆

開発「C2C資産の削除は不可逆」／QA「30件クローズのうち #70・#96・#79 は**テストそのものが主成果物**だった」／UI・UX「凍結対象コードの整形に工数が乗る」／データ「ルールのロールバックは画面が落ちてからしか気づけない」。

## 3. 部署間で意見が割れた点（＝社長の判断が要る）

### 対立A — 未デプロイ分を「まとめて出す」か「経路を絞って出す」か

| 立場 | 主張 |
|---|---|
| **開発・QA**（早く出したい） | 未デプロイのまま機能を積むと、デプロイ時に一括で不整合が噴出し切り分け不能になる。「1回デプロイして通す」ことが先 |
| **データ**（止めたい） | **一括デプロイに反対**。`storage.rules` は本番Consoleで直接編集された旧版との乖離疑いがある。リポジトリ版は5MB上限・`documents/` 本人限定という具体的な制限を持つため、**本番側が緩い旧ルールなら、出した瞬間に既存ファイルの読み取りが落ちる** |

**判断に要るもの**: 本番の現行 `storage.rules`（Firebase Console のルール履歴タブから取得可能）。これが取れるまでどちらも正しい。

### 対立B — 「効率化」の効き先が実装側にあるか

| 立場 | 主張 |
|---|---|
| **開発** | 実装側に効率化の余地はほぼ無い（全件パス・クリーン）。ここへの投資は測定上の改善に見えるだけ |
| **QA** | むしろ**検証が薄くなった**。`ci.yml` の push トリガーを main のみにした結果、ローカルにFlutter SDKが無い環境では「PRを開くまで一切の検証が走らない区間」が生まれた。CIは冗長な検証ではなく**唯一の検証** |
| **UI・UX** | 効率化が「滞留PRの処理」に読み替わると、より上流の**IA不整合（B2Cの5タブ構成のまま）が温存される**。`FleetDashboardScreen`（784行）はルートに無く、ホーム画面からの遷移でしか到達できない |

### 対立C — B2C資産をどう扱うか

| 立場 | 主張 |
|---|---|
| **開発** | 42サービス／33モデルのSNS系がテスト・CIの全実行に乗り続けている。fleet系画面は2枚のみ。**資産の重心とB2Bの重心がずれている** |
| **QA** | 削れば凍結解除時にゼロから作り直す。維持コストは測定可能だが、削除の機会損失は測定できない |
| **UI・UX** | そもそも「凍結」の粒度が未定義。`FeatureFlagService` の `remoteKeys` は `c2c_parts_marketplace` の1件のみで、SNS/ショーケース/出品は同じ制御下に無い |

## 4. 各部署の回答（全文）

<details>
<summary><b>開発部門</b></summary>

### 論点
1. **「効率」の対象は開発スループットか、凍結判断までの時間短縮か** — 前者はCI/ブランチ整備、後者は最小限のfleet導線を1社に触らせる段取りに寄る。投資先が正反対。
2. **人間ボトルネック（rules 785行・indexes 45本が未デプロイ、設定ファイル未配置、Apple承認待ち）を誰がいつ解くのか** — デプロイ権限者の稼働枠を確保するのか、権限自体を移すのかは別の決断。
3. **C2C資産（42サービス/33モデル）をどこまで維持コストとして払うか** — 残置・削除・FeatureFlag遮断のどれを選ぶかで今後の全変更のレビュー範囲が変わる。
4. **`origin/claude/*` 66本をどう扱うか** — 一括削除は転用候補を失う。残せば main との乖離が進む。「いつまでに転用判断しなければ捨てるか」の期限が分岐。
5. **ローカルFlutter SDKなし・CI委譲という現体制を固定するか** — 1変更あたりの試行回数が変わる。
6. **B2Bの「1社目」を誰にするか、要件をコードより先に確定するか** — 決めずに効率化すると、速く外れる。

### 反対する理由
- 効率化の対象が実装側にない。詰まりは人間側。リードタイムは1日も縮まらない可能性が高い。
- 未デプロイのまま速度を上げると、検証されていないコードが増える。
- ブランチ66本の整理はB2B転用候補5件の目利きと不可分。機械的に掃除すれば転用可能な実装を捨てる。丁寧にやるなら効率化ではなく調査コストの前払い。
- 凍結の可能性がある案件に基盤投資をすると埋没する。回収に数ヶ月かかる。
- C2C資産の削除は不可逆。残置コストは測定可能だが、削除の機会損失は測定できない。

### 足りない材料
- B2B見込み顧客リストと反応の有無（営業/社長）— 「反応がなければ凍結」の判定基準が言語化されていない
- rules/indexes をデプロイできる人・アカウントとその空き時間（Firebaseオーナー権限保有者。IAMで即判明）
- `origin/claude/*` 66本の内訳（GitHubのPR/ブランチ履歴から機械的に棚卸し可能。現ローカルクローンには2本しか無い）
- B2B想定顧客の実運用要件（台数規模、管理者/ドライバーの権限分離、車検・点検の運用フロー）
- 月額ランニングコスト（Firebase従量・Actions分数・Apple年額）— 請求画面から取得可能。凍結判断の分母

</details>

<summary><b>QA部門</b></summary>

### 論点
1. **「テストが緑」の定義をどこに置くか** — 3284件は `fake_cloud_firestore`(27ファイル)／`mockito`(34ファイル)によるインメモリ検証で、**セキュリティルールを一切評価しない**。`firestore.rules` は785行・約48コレクションだが、`test/rules` が実際に検証しているのは `accessory_showcases/*/comments` と `vehicle_sharing_permissions` の**2領域のみ**。
2. **未デプロイのルール／インデックスを品質ゲートに組み込むか** — `firestore.indexes.json` は45インデックス・JSONコメント入りで、**CIに構文/整合性の検証ジョブが存在しない**。
3. **B2B転換後、テスト資産のどこを「維持対象」と宣言するか** — `test/services` 52ファイルに凍結済みB2C/C2C系が残る。
4. **`claude/**` push でCIを外した穴を何で埋めるか** — pre-push hook・ドラフトPR即時作成・週次フルCIのいずれか。
5. **`continue-on-error: true` のエミュレータ結果をどう扱うか** — `test/integration` 7ファイル（うち4つが `emulator` タグ）が**恒常的に無視されている可能性**。
6. **凍結時に何を残せば再開可能かの基準を先に決めるか**

### 反対する理由
- **「効率化」の実績が既にテスト資産の消失として現れている**。30件クローズのうち #70（ShopComparisonScreenテスト15件）・#96（12件）・#79（Haversineテスト補強）は**テストが主成果物**だった。整理の速度指標にテストは映らないため、次も同じ経路で消える。
- 効率化＝実行回数削減になり、唯一の実測手段が細る。CIは「冗長な検証」ではなく**唯一の検証**。
- 3284件という数字が安全マージンとして誤読されるリスク。実体はルール未検証・本番未反映。
- B2B転換で「テストが無い領域」に開発が集中する。**新規性が最も高い領域が最も検証の薄い領域**。欠陥は権限まわりに出る。
- `continue-on-error` の常態化が「緑の意味」を侵食する。`pm_report.yml` が8/8全失敗のまま放置された前例が、この経路の実在を示している。

### 足りない材料
- カバレッジの実測値と分布（CIは `--coverage` を取り Codecov に送っているが `codecov.yml` が無く閾値もない。lcov から `fleet_*` だけ切り出せばB2B領域の薄さが出る）
- 本番Firestoreの現行ルール／インデックスとリポジトリの差分（Firebaseオーナー。`--dry-run` かConsole履歴）
- エミュレータ系ステップの実際の成功率（Actions のラン履歴をAPIで集計すれば統合テスト7ファイルが実質死んでいるか判定できる）
- **B2B顧客側の受け入れ基準**（何が壊れたら業務が止まるか。車検期限通知の欠落か、CSV出力の欠損か、権限の誤許可か）— 社長／想定顧客しか持たない
- 凍結済み機能の復活可能性の見積り（ロードマップ決裁者）

<summary><b>データ部門</b></summary>

### 論点
1. **`vehicles` をB2C/B2B兼用のまま使うか、フリート専用に分離するか** — `FleetService.getCompanyVehicles` は `vehicles.where('companyId')` で引くが、`firestore.rules` の `vehicles` は読み取りを `resource.data.userId == request.auth.uid` にしか許していない。**ルール未デプロイ以前に、この形はクエリごと拒否される**。後から変えると移行スクリプトが要る。
2. **月次レポートを都度集計かFunctions事前集計か** — ルールは `shop_monthly_reports` を「Functions専用書き込み」と宣言済みだが、実装済みの `getMonthlyReport` は `inquiries` を2ヶ月分全件取得してメモリ集計。**設計が二本立て**で、表示回数と読み取り課金が比例する。
3. **未デプロイ分をどこまで出すか（範囲＝本番の面積）** — ルールのトップレベル match は51、indexes の collectionGroup は18、`fleet_*` のインデックスは**0本**。
4. **継続/凍結を何の数字で判断するか** — `analytics_service.dart` のイベントは `vehicle_added` `shop_viewed` `inquiry_sent` などB2C前提のみ。**フリート登録・メンバー招待・CSV出力・レポート閲覧は計測されていない**。参照箇所も5ファイル。
5. **コスト前提を置き直すか** — `OPERATIONS_COST_ESTIMATE.md` はMAU 1K/10K/100KのB2C前提。同文書が「監視対象」とする `community_maintenance_trends` / `faqs` のインデックスは**実ファイルに存在せず、文書と実体が既に乖離**。

### 反対する理由
1. **「滞留分の一括デプロイ＝効率化」に反対。** `storage.rules` の本番乖離疑いと衝突する。本番側が緩い旧ルールなら、出した瞬間に既存ファイルの読み取りが落ちる。ルールのロールバックは画面が落ちてからしか気づけない。
2. **インデックスを足す方向の効率化は書き込みコストと逆相関。** `inquiries` だけで既に7本。足すほど1件の書き込みが重くなる。
3. **シード未実行のまま反応を測るのに反対。** `safety_tips` / `community_maintenance_trends` は空のはず。画面が空でも「顧客が反応しない」のか「データが無い」のか区別できない。
4. **UI配線を先行させることに反対。** 論点2が未決のまま `getMonthlyReport` を画面に繋ぐと、Functions集計へ寄せる際に Service・ルール・インデックスの3層を作り直すことになる。

### 足りない材料
1. 本番に実デプロイ済みのルール／インデックス（Console権限者）— `firebase firestore:indexes` の本番出力とリポの差分、Consoleのルール履歴
2. `storage.rules` の本番現行版（同上）— **これが取れるまでデプロイ可否は判断材料が無い**
3. 実課金額と実リクエスト数（Console の Usage / 請求）— 試算がすべて机上の仮定値
4. B2Bの利用単位（1社あたり車両台数・担当者数・レポート閲覧頻度）— 営業・ヒアリング先
5. 本番の実データ件数（`inquiries` 総数、`companyId` 付き `vehicles` 件数）

<summary><b>UI・UX部門</b></summary>

### 論点
1. **B2Cで作った5タブのルートIAを、いつ・誰の職務動線に組み替えるか** — `home_screen.dart:218-` のルートは「マイカー／マーケット／みんなの投稿／通知／プロフィール」で全面的にB2C個人視点。社用車管理の中核 `FleetDashboardScreen`（784行）は**ルートに無く**、`home_screen.dart:551` と `:1610` からの遷移でしか到達できない。**B2B転用とは実質このIA転置**であり、#98のトークン統一より上流の分岐点。
2. **B2C画面を「凍結」と呼ぶとき、導線非表示・コード残置・削除のどれを指すか** — `FeatureFlagService` の `remoteKeys` は `c2c_parts_marketplace` 1件のみ、既定は `NoopRemoteFlagSource`＝実質ローカル既定値固定。SNS/ショーケース/出品は同じ制御下に無い。
3. **PCブラウザを一級の対象にするか、モバイル画面の流用で済ませるか** — `DESIGN_SYSTEM.md:527` に `Breakpoints`（600/900/1200）の定義があるが、**`lib/` 側に実装が1件も存在しない**。`LayoutBuilder`/`kIsWeb` を使うファイルは全201ファイル中5件。法人向けウェブ管理画面は既存資産の再利用ではなく**新規レイヤー**になる可能性。
4. **「統一」の対象はウィジェット統一かトークン遵守か** — `Colors.blue/grey` 等の直書きが画面層に77箇所。#98が扱うのは一部で、両者は別作業。
5. **前提の鮮度を誰がいつ再確認するか**

### 反対する理由
- 「効率化＝滞留PRの処理」に読み替わると、IA不整合が温存される。#98を再開してもタブ構成はB2Cのまま。
- **前提が既に古い**（→ §0 で PM が裏取り済み。指摘は事実）
- Web対応の見積りが過小になる恐れ。ブレークポイントは文書のみで未実装。#108のWeb対応は「Webで動く」であって「PCで使える情報密度」ではない。
- 凍結対象コードが残置のまま統一作業の対象に含まれ、捨てる画面の整形に工数が乗る。

### 足りない材料
- 社用車管理の実利用者像と職務動線（管理者／ドライバー／工場の3者で画面が分かれるのか）
